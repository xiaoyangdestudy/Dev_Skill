# 工作流细则

## 阶段判断

### 资料接入
至少有一个原始材料目录或用户明确提供了需求、设计、接口、H5资料。

### 需求分析
尚无可靠的范围边界、用户流程、责任边界或待确认项清单。

### H5/接口审查
需求梳理已有初稿，需要确认跨端调用链、接口参数、响应或错误处理。

### 技术设计
需求和接口审查已形成可执行结论，且需要结合代码库决定修改位置和顺序。

### 测试准备
技术设计已经明确，需要把功能和边界转换成可执行测试用例。

### 实施中
用户明确要求写代码，或项目已有代码变更需要记录和验证。

### 验收
已有测试执行结果、联调证据、截图/日志或用户明确要求验收。

## README 规则

每个由项目维护、可供 AI 导航的文件夹都应有 `README.md`。README 内容保持短小：

- 目录用途
- 文件/子目录索引
- 资料来源或生成方式
- 当前注意事项
- 不确定内容的入口

不要把原始材料全文复制到 README；不要把分析结论同时维护在多个 README 中。根 README 只做总索引，子目录 README 只做局部索引。

## 文档更新规则

- 已有同名文档：先读取，再增量更新；保留人工确认内容。
- 没有同名文档：按模板创建。
- 同一事实只保留一个主要来源，其他文档使用相对路径引用。
- 每次重要更新在文档末尾增加简短“变更记录”，不要生成重复版本文件。
- 原始材料不移动、不重命名、不覆盖；除非用户明确要求。
- 绝不把示例字段、推测的接口响应或常见产品行为写成已确认事实。

## 证据等级

按以下顺序判断可信度：

1. 用户明确确认
2. 当前代码和真实执行结果
3. 后端/H5/产品提供的正式资料
4. 设计结构化数据或设计稿
5. AI 对资料的分析
6. AI 的推测

第 5、6 级不能直接写为确定契约；第 6 级只能作为待确认问题的可能解释，并明确标注。

## 低 Token 读取策略

1. 先读当前目录 README。
2. 根据 README 选择相关子目录。
3. 先读分析文档，再回到原始材料核对细节。
4. 设计任务只读取相关页面和结构化节点；接口任务只读取相关接口及样例。
5. 开发任务只读取相关代码入口和依赖链，不扫描无关模块。
6. 历史进展只读取与当前任务有关的最近内容。
7. 输出结论时引用路径，不重复粘贴原文。


## 需求访谈 / 迭代澄清

在形成《01_需求梳理与范围边界》时执行，不调用其他 Skill：

1. 先读项目和材料目录 README，再读取需求、设计、接口中与当前功能相关的证据。
2. 用自己的话简短复述已理解的目标、范围和关键流程；区分“材料明确”“代码现状”“尚不明确”。
3. 找出会改变功能范围、用户行为、跨端责任、接口契约或验收条件的歧义，检查是否能从现有本地材料/代码中回答。
4. 每轮只问最重要的一个问题；只有紧密相关、必须一起回答的问题才合并。说明依据、缺口和影响，选项只能作为方便回答的参考，不得把猜测伪装成默认答案。
5. 等用户答复后，将答复作为用户确认的事实写入 01 文档和项目 README 对应摘要，再判断下一个最重要的问题。不要一口气倾倒所有问题，也不要反复询问已确认内容。
6. 若用户没有回答、要求先继续或该问题不阻塞其他部分：把它标记为待确认并写明影响/阻塞范围；只继续独立部分。依赖该答案的行为、技术决策和验收预期保持未定。
7. 当关键范围足够清楚时，简要复述将写入的需求基线，请用户纠正明显误解；用户确认或明确要求直接继续后，形成当前需求基线。

提问应像有经验的评审者：发现冲突、追问隐含假设、把模糊词转成可判断的行为；但不为了“刁钻”而增加无价值问题。
